## The content layer

Articles live in `Website/src/content/articles/` as MDX files. Astro's content collections type-check the frontmatter at build time — title, date, excerpt, tags, draft flag. The slug comes from the filename.

MDX gets rendered at build time. No client-side markdown parsing, no JavaScript fetching content on load. The page that reaches you is static HTML[EY1 CH T IY1 EH1 M EH1 L]. Astro ships zero JavaScript by default, so the only scripts on an article page are the audio player and a small toggle for the raw TTS script view — hit **see raw script** at the top of any article to see exactly what text gets fed to the voice model.

## Phoneme annotations

The TTS model — OmniVoice, released by k2-fsa — uses CMU[S IY1 EH1 M Y UW1] ARPAbet[AA1 R P AH0 B EH2 T] phonemes. Acronyms and unusual terms get annotated inline in the MDX:

```
The API[EY1 P IY0 AY1] handles the request.
```

The display layer strips the `[...]` part so the reader sees "API". The TTS pipeline receives the phoneme sequence instead of the raw letters. Without this, OmniVoice would read "API[EY1 P IY0 AY1]" as "ah-pee" or "SQL[S IY1 K W AH0 L]" as something that doesn't resemble "sequel." A maintained table of annotated terms lives in the article skill, so new articles get consistent pronunciation without re-solving the same phoneme lookups.

The same annotation system also handles paralinguistic markers — pauses, soft questions, mild surprise — placed at the start of sentences to shape delivery. These are stripped from the display entirely.

## Audio generation

A Python script runs locally before committing. It takes a slug and does five things:

First, it reads the MDX file with explicit UTF-8 encoding. That matters on Windows, where the default encoding decodes em dash bytes as a euro sign, which OmniVoice then reads as "euro." Every em dash becomes a comma for a natural pause. Regular hyphens stay — "real-time" should sound like "real-time," not "real, time."

Second, it strips MDX syntax: frontmatter, import/export statements, HTML[EY1 CH T IY1 EH1 M EH1 L] tags, markdown links (keeping the display text), bold, code spans, code blocks. Headers get an ellipsis before and after to create a beat between sections.

Third, phoneme annotations flip: `word[PHONEME]` becomes `[PHONEME]`, dropping the written form. A word substitution map handles terms OmniVoice consistently mispronounces regardless of phoneme markers.

Fourth, the cleaned text goes to OmniVoice running on CUDA with a reference voice sample. The same wav file is used every time, so every article has the same voice. Speech speed is set to 1.15x — slightly faster than the model default, which reads a little slow.

Fifth, the output writes to a FLAC file and a waveform JSON. The waveform is 200 normalised peak values between 0 and 1, computed by chunking the audio samples and taking the max absolute amplitude per chunk.

## The player

The article page checks at build time whether the FLAC exists. If it does, a player renders above the article body. If not, nothing renders — there's no broken UI or missing element, the section just isn't there.

The waveform is a `<canvas>` element. The 200 peak values draw as rounded bars scaled to canvas height, accounting for device pixel ratio. Bars left of the playhead render full white. Unplayed bars render at reduced opacity scaled by their amplitude, so quieter sections look visually quieter.

The seek input overlays the canvas at zero opacity. Clicking anywhere on the waveform scrubs the audio without any visible range input. Volume is a separate control.

The `<audio>` element uses `preload="metadata"` so duration loads on page paint without buffering the file.

## How it fits together

The FLAC ships with the static build and serves from Cloudflare's CDN[S IH1 D IH0 EH1 N]. No API[EY1 P IY0 AY1] calls at read time, no server processing, nothing to go wrong in production. The expensive part — the TTS inference — runs once on my machine before the commit. After that it's just a file.
